# Decisions

Each item gives the decision, the evidence, and what would reopen it. Items 1 to 7 were settled with the product specification on 2026-10-14; the rest were settled during the pre-implementation pass on the same day. Spike runs were made on Windows 11 Pro 10.0.26200 with Claude Code 2.1.296, Node 26.4.0, gh 2.91.0 and git 2.56.0; the raw artifacts live outside the repository.

1. **A self-contained repository.** Every file is written for this suite. No file imports history, links to another project, maps names, records an acceptance run made elsewhere, or notes what came before. Lessons enter the requirements as rules with no source line. Reopens: never; this is the premise of the repository.
2. **Plugin names `rules`, `loop`, `audit`, `repo-docs`.** They give `/rules`, `/loop:run`, `/audit:run` and `/repo-docs`. Spike 8 confirmed that a skill named like its plugin answers to the bare `/rules` as well as `/rules:rules` on 2.1.296; the documentation describes only the namespaced form, so the README shows both. The spike says nothing about a name a bundled skill owns; see decision 35 for `loop`. Reopens: a host release where the bare form stops working, which the acceptance item for `/rules` would catch.
3. **`repo-docs` is written from its requirements alone.** Requirements 197 to 212 specify the model, the pointer grammar and the hook in full; nothing is copied from another plugin. Reopens: never.
4. **Both house-rule edits ship.** The two Working items in requirements 19 and 20. Removing any stop was rejected. Reopens: the owner's say-so.
5. **No effort tiers in the loop.** One default run budget of 240 minutes, the risk floor, and a prose effort hint. A tier would choose a model per step, and the suite has one model per role, so a tier could only set the budget, which the hint and `.reimagine.json` already do. Reopens: field runs that need a budget the hint and the configuration cannot express.
6. **State directory `.reimagine/`, namespaced per plugin.** The loop writes `.reimagine/loop/<branch-slug>/` and adds `.reimagine/` to `.git/info/exclude`; the audit writes `.reimagine/audit/<run-id>/` only when `.reimagine/` is already ignored, and otherwise falls back to the plugin data directory, because the audit never writes under `.git/`. The specification named `.reimagine/<branch-slug>/`; the extra level keeps a branch slug from colliding with an audit run id. Repository configuration is `.reimagine.json`. Reopens: a host feature that gives plugins a per-repository ignored directory.
7. **Azure DevOps pull request publishing is out of scope.** Reads and discussion comments go through an MCP tool or `az`; a run on an Azure DevOps remote ends `prepared` with the push command. Reopens: a tested `az repos pr create` path with an acceptance item.
8. **No attribution hook.** Spike 5: with the attribution setting off, three of three commit runs on 2.1.296 (opus, sonnet, opus) produced no trailer; with it on, the model added one and said the session setup told it to. A hook denying a commit that carries a trailer while the setting is off would guard against a behavior that did not occur. Requirement 11 keeps the rule that the loop never types a trailer. Reopens: a trailer appearing in the field with attribution off.
9. **No `userConfig` anywhere.** Spike 4: a boolean option with `default: true`, referenced as `${user_config.flag}` in a hook command, failed every run while unset with `Plugin option "flag" isn't set. Open /plugin manage to configure it`. The default was not substituted. Options are expressed in `.reimagine.json` or in prose instead. Reopens: a host release that substitutes defaults, confirmed by rerunning the spike.
10. **Forbidden names are enforced from outside the repository.** A list of forbidden names inside the repository would itself be a file holding them. Lint reads `LINT_DENY_TOKENS` from the environment when set and fails on any tracked file containing a listed token; CI leaves it unset and the implementing session sets it locally before every commit. Reopens: never; the need ends with 0.1.0.
11. **Fixture literals are observed, not computed.** The audit script suites compare bytes and shas that embed strings (`reimagine-handoff: 1`, `# audit report: `, `audit:auditor`, the `working-tree.sh` commit identity, the fixture handoff blob). Every literal that depends on such a string is produced by running the fixture builder once and pasting the observed value, in its own commit, so the diff shows which values follow from which strings. Reopens: never.
12. **`jq` is an optional prerequisite of the audit.** Three scripts need it; Git for Windows does not bundle it; a Node rewrite would add code without a suite behind it. The README names it and stage 1 warns when it is missing. The repo-docs hook stays free of it. Reopens: `jq` installs proving a recurring support cost, which would justify the rewrite with its own suite.
13. **The credential scan belongs to the loop.** The specification places the scan on ticket text before it is written to a run directory. The loop writes ticket text into its record, so it scans. The audit redirects forge reads to files without passing them through the model and keeps its run directory ignored; adding a scan there would be new scope. Reopens: a field run where audit run-directory contents leak into something published.
14. **Trigger phrases live in the skill description.** Spike 1: a description naming "reimagine loop" and "run the loop" invoked the skill in two of two opus runs; a terse description without the phrase also invoked a skill named `loop` once; a negative control did not. `when_to_use` is not used because the spike did not cover it and the host appends it to the description anyway. Reopens: a trigger miss in acceptance.
15. **Reviewer fallback is written into the skill.** Spike 2: `fable` and `opus` are accepted agent model names on this account; an unknown name fails the Agent call with an API 404 that the orchestrator sees. The skill retries once at `opus` on a model or tool error, records the swap, and stays swapped. Reopens: a host feature that falls back by itself.
16. **`steps.json` is the loop's completion record.** Parsing prose for resume is fragile; a JSON entry written `complete` only after its outputs exist is a reliable single source, and the audit's `stages.json` follows the same pattern. `run.md` stays the narrative. Reopens: never.
17. **The diff review has a defined request.** Requirement 66 states what a diff reviewer receives: plan, inputs, acceptance criteria, dispositions, and the diff read from the merge-base after `git add -N`. No credential scan runs on the diff: it stays with the session's own model provider. Reopens: a finding that a reviewer subagent surfaced a credential into the record.
18. **Review calls get a 30-minute budget.** A live run's final review over 37 files took 20 minutes 42 seconds and blocked at a 20-minute budget with no path to resume. Review passes have their own `review` budget of 30 minutes, and the idempotent record lets a blocked step 5 be rerun. Reopens: budget data from the first ten field runs.
19. **A missing `code-review` skill does not block a higher-risk run.** An Opus subagent reviewing a patch file serves worktree and additional-repository diffs; the same path serves when the skill is not listed. Reopens: never.
20. **The loop edits only pull request bodies it wrote.** A body belongs to whoever wrote it. A pull request this loop opened is recorded in `steps.json` and its body is updated once per run; a pull request the loop did not open gets a comment only. Reopens: never.
21. **Second opinion: sentinels, 60-id batches, one launch per batch.** Sentinels prove the agent read each input and feed the low-tier gate credit. Batches of 60 keep one answer within a size the orchestrator can check position by position; the number is revisited when a run shows a reason. There is no follow-up call and no inline input form: an unacknowledged input fails the stage, and the ladder relaunches. Reopens: a run where batching changes the verdict.
22. **Four audit commands.** `run`, `resume`, `act` and `handoff` are thin forwarders; `resume`, `act` and `handoff` take their few flags because they take ids and files, not prose. The prose form "reimagine audit ..." is the primary entry. Reopens: never.
23. **`commit: true` snapshots go to `docs/runs/<branch-slug>/`.** Each publishing run commits the plan and `report-<n>.md` with state `publishing`; the terminal report is posted as a pull request comment. Reopens: a repository convention that names another place, which `repo-docs` placement would then follow.
24. **Mechanisms not built, and why.** A one-request-per-session implementer transport: slices run in parallel when their files are disjoint. A model-provider availability probe before a run: the host is the only provider. Request files and thread ids for reviewers: each review is a fresh Agent call with the request in its prompt. A no-retry rule for a process that may outlive its call: subagents end with their call. A 3,600-second cap on implementer timeouts: budgets are minutes in `.reimagine.json`. A headless cap on the second opinion: it is an Agent call under the orchestrator's budget. Running the second opinion from the repository root: the agent reads absolute paths. A version gate between plugins: no plugin depends on another. An on-off option for a provider: there is one provider. Sending an empty diff to review: the step records "no changes" instead. Each is recorded so nobody adds it without a new reason. Reopens: never.
25. **The staleness notice display is an acceptance item.** Spike 3 showed the hook running with outcome success and the `systemMessage` JSON on stdout, but a headless run cannot show what the user sees. Reopens: never; it is checked interactively.
26. **The idempotency spike ran on git primitives only.** Spike 7 verified merge-base, explicit-refspec fetch, fast-forward over a foreign commit, an append-only record under `.reimagine/` excluded from status, the remote-head check, the three-dot diff, and the existence of `gh pr edit --body-file` and `gh pr comment --body-file`. A second invocation of the skill on a branch with an open pull request cannot run before the skill exists, and opening a pull request needs its own ask. That run is the acceptance item of the idempotency milestone. Reopens: never.
27. **CI pins a Claude Code version at least seven days old.** The validate job installs a fixed version with the autoupdater disabled so a new release cannot change the result without a commit here. 2.1.296 is the version the spikes ran on and is recorded in acceptance.md; the pin is chosen when the CI milestone lands. Reopens: a validation change in a newer host release.
28. **Hub cap 60 lines, spoke cap 200.** The specification named about 60 for the hub; 200 follows the host's guidance that each instruction file stay under 200 lines. Reopens: a host change in context handling.
29. **One script for the rules plugin.** The staleness notice is the `session-start` verb of `rules.mjs` rather than a module of its own; the script budget is 700 lines. Reopens: never.
30. **No loop commands at all.** "plan only" is a mode read from prose, and the skill itself is named `run`, so `/loop:run` is the skill and there is no command file. Reopens: never.
31. **Deferred audit helpers.** A stage 4 and 5 bookkeeping helper, `ledger.sh build6`, `report-parts`, `count`, and an Azure DevOps exporter are not built; each needs fixtures and a design review of its own. Reopens: a field run where hand bookkeeping slipped, recorded as an issue.
32. **The marketplace `metadata.version` is the catalog's own.** With no suite version, it is raised whenever an entry changes, and lint only requires it to be present and well formed. Reopens: never.
33. **Implementers are told to stay in scope.** A live run saw an implementer widen a `gh` command unasked and a brief cause a defect; requirement 104 makes the brief say so, and the slice review catches it. Reopens: never.
34. **Baseline failures match by test name.** Two of sixteen baseline failures in a live run passed later, so counts are not a stable match. Reopens: never.
35. **The loop plugin keeps its name; its skill is `run`.** Claude Code 2.1.296 bundles a `/loop` skill that runs a prompt on an interval, so the bare `/loop` is taken. The plugin stays `loop` (decision 2), its single skill is named `run` and answers only as `/loop:run`, "reimagine loop" is the primary trigger phrase and "run the loop" the secondary one, and acceptance item 25 checks that both reach this skill and that the bare `/loop` is the host's. Renaming the plugin was rejected because it would change every document and the catalog before anything is built. Settled 2026-10-14 by the owner. Reopens: acceptance item 25 showing the secondary phrase reaching the bundled skill, which would drop the phrase.
36. **An existing record is found by ticket id.** The predicted branch is built from every ticket in request order, so adding or reordering tickets changed the name, missed the record and would have opened a second pull request. Step 0.2 reads the `tickets` list of each record's `steps.json` before it predicts a name; one match is continued, several stop the run with the "continue <branch>" form. Requirements 49 and 83 name this lookup. Settled 2026-10-15. Reopens: a field run where the stop for several matches costs more than naming the branch.
37. **Steps 1 and 2 record input versions, not the hash of `inputs.md`.** Every run appends a section to `inputs.md`, so its hash never matches on a rerun and an interrupted run could not resume after Step 2. Each open input records the version its host reports, or the hash of its file. A comment on an open ticket counts as a change and reruns its verification, which is the safe side. Settled 2026-10-15; acceptance item 10(e) resumed at Step 3 with it. Reopens: a host whose version moves without an edit often enough to cost reruns.
38. **Per-run files take a run suffix.** Requirement 86 forbids rewriting a prior run's files, and the body, ticket comment and patch names were fixed, so from run 2 on they take `-run<n>`; the counters keep `pre-<n>`, `comment-<n>` and `text-<k>` apart. Settled 2026-10-15. Reopens: never.
39. **A ticket done at preflight gets no comment.** Requirement 90 says a run with no new work posts nothing, and a run that adds tickets reports on the new ones; a status comment on a finished ticket in every run would only repeat itself. Settled 2026-10-15. Reopens: a reviewer asking for a status line on every ticket of the pull request.
40. **The posted report leaves out the header lines that name local paths.** Under `commit: true` the record, worktree, repositories, handoff and audit lines name paths on the user's machine, which no published text names, so the external form drops them and keeps the rest of the header. Under `commit: true` that comment is the run's one comment on the pull request. Settled 2026-10-15. Reopens: never.
41. **No new work ends `done` only on published work.** A run whose inputs are all done counts its work as published when the run that last wrote Step 7 ended `done` and its pull request is open; otherwise Step 7 runs, pushes what the remote lacks and watches CI. Without this rule a run whose commits were never pushed, or whose CI was red, would end `done` with nothing anyone can review. Requirement 90 states the rule. Settled 2026-10-15 after a code review of the idempotency rules. Reopens: a host where the loop cannot tell whether its work is published.
42. **A slice committed by hand is found by its file hashes.** A `prepared` run leaves its work uncommitted and the user commits it with the report's commands, so no commit line in `run.md` names it. Each slice a run built and did not commit records the blob hash of each file it owns, and a later run counts it committed when the branch tip holds those blobs. Matching a foreign commit by its paths alone was rejected, since an unrelated commit can touch the same files. Settled 2026-10-15. Reopens: field runs where users edit the work before committing it, which leaves the slice open.
43. **A record whose pull request merged or closed is finished.** A reopened ticket finds its record by ticket id, and without this rule the run would judge it done or continue a branch whose pull request is closed. Preflight ends `blocked`, naming the pull request and the "on branch <name>" form that starts a new branch. Starting a new branch on its own was rejected because it changes branch prediction (requirements 77 and 83). Settled 2026-10-15 by the owner. Reopens: a team that reopens tickets often enough that the stop costs more than a suffixed branch name.
44. **No `inline_cap_bytes` fault.** The second-opinion request has one form: it names every input copy by path and carries no inline content, so no size cap exists for a fault to lower. Requirement 187 lists the six remaining `_test` keys. Settled 2026-10-15. Reopens: an inline request form.
45. **Two disclosed writes under the git directory.** An approved fetch writes remote-tracking refs, and `working-tree.sh build` writes loose objects for a `head: working-tree` bundle; both are listed in the read-only boundary of `common.md` and in the report. Requirement 175 names them as the only exceptions to "never writes under the git directory", since the two sentences read as a contradiction without it. Settled 2026-10-15. Reopens: a way to pin a working tree without an object write.
46. **A prerelease catalog on `main`.** The owner wants the built plugins on a work machine before the suite is complete, and a catalog that names `repo-docs` before it exists fails to install. The catalog on `main` lists only built plugins; requirement 1 keeps the four-plugin catalog as the 0.1.0 state. Settled 2026-10-15 by the owner. Reopens: 0.1.0, when the catalog lists all four.
47. **Prerelease versions `0.1.0-alpha.<n>`.** A built plugin ships at a semver prerelease that sorts below 0.1.0, so the first release stays 0.1.0 and an installed alpha updates to it. The audit's `plugin_version` literal follows the manifest, so a run made under an alpha reruns stage 1 under the next version. Settled 2026-10-15. Reopens: never.
48. **Prerelease tags get changelog headings.** A tag `<plugin>--v0.1.0-alpha.<n>` is a tagged version like any other, so requirement 15 gives it a heading; a release with no tag gets none. Settled 2026-10-15. Reopens: never.
49. **A hub is a file with a `## Spokes` line.** The drift hook runs in every repository once the plugin is installed, so a long `CLAUDE.md` in a repository that never ran `/repo-docs` would have every commit denied for its length. The hook treats the root `CLAUDE.md`, or the `AGENTS.md` that an exact `@AGENTS.md` adapter names, as a hub only when it holds a line exactly `## Spokes`; otherwise it prints nothing, which is how requirement 210's "no hub" is checked. The adapter is one line, `@AGENTS.md`, with an LF or CRLF ending or none; an adapter whose `AGENTS.md` is missing is no hub. Settled 2026-10-15. Reopens: a request to warn in repositories not yet adopted.
50. **The hook checks the repository the commit runs in.** The base directory is the `cwd` field of the hook's input, else the hook's own working directory; each `-C <dir>` and `--work-tree <dir>` of the commit is applied to it as git applies `-C`, and `git rev-parse --show-toplevel` gives the root. A leading `~` in a directory becomes `$HOME`; a directory that does not resolve, such as one written with a shell variable the hook never expands, falls back to the base directory. A `cd` before the commit in the same command is not followed. Git itself runs only for that root and for the changed set of decision 56; requirement 211's list names the text tools the hook may use besides it. Settled 2026-10-15. Reopens: a field commit after a `cd` into another repository that the hook missed.
51. **A malformed index line denies.** Requirement 199 has the hook test the pointer form, and a malformed line names a path the hook cannot check, so it denies with `<file> has a malformed index line: <line>`, beside the two findings requirement 210 lists. Findings are joined with `; `, per file its cap finding first and then its index lines in order, files breadth first from the hub. Settled 2026-10-15. Reopens: field reports of denials for lines that were meant as prose.
52. **Spoke indexes and coverage.** A spoke's own pointers are the column-0 `- ` lines under its own `## Spokes` line, in the same form, followed to any depth with each file read once; prose bullets elsewhere in a spoke are never read as pointers. An index runs from `## Spokes` to the next level 1 or 2 heading. A pointer's coverage is every backticked token without a space in its condition clause, the text after the first full stop and space outside backticks, that names an existing file or directory, so a word in the first sentence or a bare command name never becomes a prefix; a pointer with none covers its spoke's directory when the spoke sits beside code, and nothing when it sits at the root or under `docs/`, since a `docs/` page would otherwise cover every other page there. Settled 2026-10-15. Reopens: a spoke layout this misses, seen in the field.
53. **What pins a file, and what a move commit holds.** Requirement 204 forbids moving a file something depends on, naming links, while requirement 205 repairs inbound links in the same change as a move. A file is pinned by an `@` import of it, by a reference from a file that is not documentation (code, configuration, CI, a package manifest), or by a fixed name other tools read (`README.md`, `CLAUDE.md`, `AGENTS.md`, `CONTRIBUTING.md`, `CHANGELOG.md`, `LICENSE`, anything under `.github/`). A link from a documentation file does not pin it: the move commit holds the `git mv` and the path edits of those links and nothing else, so no commit leaves a broken link and every rewrite goes in a later commit. Requirement 13 governs this repository's commits, not the user's. Settled 2026-10-15. Reopens: an amendment of requirement 204 that says this itself.
54. **Who commits.** Bootstrap writes the hub and leaves it uncommitted, since it asks nothing. Adopt, and maintain when it finds drift, print a plan that lists every commit, ask once, and make those commits, so one yes answers the user's own ask-before-commit rule; maintain with nothing to fix writes nothing. A second run after adopt finds the hub and reads as maintain, which is how adopt is idempotent. Each commit body opens with `Instruction-file <mode> pass, <date>.`, so the mode is on record when the printed mode line is not seen. Settled 2026-10-15. Reopens: a request for bootstrap to commit.
55. **A nested `AGENTS.md` without a root one stays.** Requirement 202 says what a repository that keeps `AGENTS.md` does, but not what a lone nested `AGENTS.md` beside a `CLAUDE.md` hub means. A repository keeps `AGENTS.md` when the root one exists; a nested one without it is read by other tools by that name, so adopt leaves it in place and the hub points to it as a directory spoke. An import of an untracked file is reported and left in place, neither inlined nor made a pointer, since a pointer to it fails on every other clone. Settled 2026-10-15. Reopens: a team that wants the nested file converted.
56. **The recheck advice reads what the commit records, not only the index.** The hook runs before the command, so the index alone misses files the same command stages: `git add x && git commit`, `git commit -a` and a pathspec commit, the first being how Claude usually commits. The changed set is `git diff --cached --name-only`, `git diff HEAD --name-only`, and, when the command runs `git add`, `git ls-files --others --exclude-standard`. This can name a spoke for a tracked change the commit leaves out, which costs one needless recheck; missing the usual commit form cost every recheck. Requirement 209 names the index alone; the proposed amendment names this set. Settled 2026-10-15 after a code review of the milestone. Reopens: field reports of advice for changes the commit did not hold.
57. **Pointer paths and caps are checked in the working tree.** The hook checks that each named path exists and counts lines in the files on disk, not in what the commit records, since a commit's content cannot be known before the command runs (`-a`, pathspecs, `git add` in the same command). So a pointer to an ignored file passes on the machine that has it, and an unstaged edit to the hub decides a commit of unrelated files. The skill never points to an untracked file (decision 55). Settled 2026-10-15 after a code review of the milestone. Reopens: a pointer to an ignored file reaching a shared branch.
58. **Versions stay at `0.1.0-alpha.1` until the release milestone.** `main` is a release channel: an installed plugin stays cached until its version string changes, so a version change is what reaches a machine that installed from the catalog. Setting 0.1.0 in the catalog milestone would publish an untagged 0.1.0 before lint, CI and the release script exist. The catalog milestone adds only `metadata.version` (decision 32), at `0.1.0-alpha.1`; the release milestone sets every plugin and the catalog to 0.1.0 with `tools/release.mjs`, which is that script's first real use. Settled 2026-10-16. Reopens: the owner wanting 0.1.0 on a work machine before the release milestone.
59. **The drift hook reaches sessions on this repository through project settings.** Nothing in the suite edits a user's `settings.json`, so requirement 16 uses the host's project scope: a tracked `.claude/settings.json` declares this catalog under `extraKnownMarketplaces` with its GitHub source, the one users install from, and sets `repo-docs@reimagine-claude` in `enabledPlugins`. On a scratch profile, a person who opened a clone saw no dialog beyond the usual folder trust, and the host cloned the catalog and cached `repo-docs`; a headless session in that clone still loaded no plugin and let a commit through. After `claude plugin install repo-docs@reimagine-claude --scope project`, which wrote the same settings and recorded the install in the profile, a headless session listed `repo-docs` in its start event and the hook denied a commit whose hub named a missing path. So the README asks for that install once per machine. A `directory` source pointing at the checkout was rejected: it carries the same catalog name as the GitHub one a user installs, and its relative path from project settings is not documented. Settled 2026-10-16. Reopens: a host release that loads a project-enabled plugin headless without an install.
60. **A plugin change before 0.1.0 takes the next prerelease.** The `0.1.0-alpha.1` tags exist, so requirement 14's tag rule holds from the lint milestone on: any edit under `plugins/<name>/` needs `0.1.0-alpha.2` in the manifest and the catalog entry, and a tag and changelog heading when it ships, and each one reaches every machine that installed from the catalog. So plugin edits wait for the release milestone, where the 0.1.0 change carries them, unless lint finds a defect that cannot wait. Settled 2026-10-16. Reopens: 0.1.0.
61. **Lint's rules live in one Node script.** `tests/audit/lint.sh` checks the audit plugin's agent tools, `gh` hosts and merger shape in awk as part of that plugin's suite; `tools/lint.mjs` implements the repository-wide forms of R219 in Node without calling it, so `npm run lint` needs no `sh` and one file holds every rule CI enforces. The audit suite keeps its own checks. Settled 2026-10-16. Reopens: the two drifting apart on a rule both hold.
62. **What the tag rule reads.** Lint reads tags with `git tag --list`, a plugin's last tag being its highest by semver, and a plugin directory changed since that tag when `git diff --quiet <tag> -- plugins/<name>/` exits 1 or the directory holds an untracked file that is not ignored. Outside a git work tree, or in a shallow clone, the tag and changelog checks fail with a message saying to fetch the full history, rather than pass on missing data. A clone with history but no tags is caught by the changelog: a heading whose version is not the plugin's current one must have its tag, so a missing tag fails with "fetch the tags". CI checks out with `fetch-depth: 0`, which brings the tags. Settled 2026-10-16. Reopens: a release flow that writes a heading for a version it never tags.
63. **What "owner-specific" matches without a list.** Lint holds no names (decision 10), so R10's rule matches forms: an email address whose domain does not end in `.invalid` (the `git@` of an SSH remote excepted); a path under `/Users/`, `/home/` or a drive's `Users` folder whose user part is not a placeholder (`<...>`, `{...}`, a variable, `~`, or one of the words user, username, you, me, dev, name, example, runner); and a GitHub, GitLab, Bitbucket or Azure DevOps URL whose owner is not a placeholder (owner, org, example, acme, octo-org, octocat, `example-` names, `<...>`, `{...}`, `:owner`) and that is not this repository. A person's name cannot be told from other words, so it is left to the deny tokens and review; so is R44's rule that the chat block names no vendor, since a vendor list in lint would hold names decision 10 keeps out of the repository. Settled 2026-10-16. Reopens: an owner-specific string in a shipped file that these forms miss.
64. **CI pins Claude Code 2.1.296.** Decision 27 asks for a version at least seven days old by its npm publish date; `npm view @anthropic-ai/claude-code time` gives 2.1.296 as 2026-10-09T16:58:10Z, so it qualifies from 2026-10-16T16:58Z, and it is the version the spikes and the first validation runs used. The validate job installs it with `npm install -g` under `DISABLE_AUTOUPDATER=1` and runs `claude plugin validate --strict` on the root and each plugin directory with `CLAUDE_CONFIG_DIR` in the runner's temporary directory; validation needs no login, shown by a run under an empty configuration directory. The mawk job puts a link named `awk` to `mawk` first on `PATH`, since the audit scripts call `awk` and the ubuntu image may resolve it to another awk, and checks the version line before the suites run. Actions are pinned by commit sha, kept current by Dependabot. `workflow_dispatch` lets a branch run the workflow before it reaches `main`. Settled 2026-10-16. Reopens: a validation change in a newer host release, or a pinned version that fails to install.
